# 政策智能匹配应用需求文档

> 文档状态：需求与视觉稿已确认，首版已开发
> 版本：1.0  
> 更新日期：2026-09-21  
> 产品形态：嵌入载体的移动端 H5 政策服务模块，全栈真实数据应用

## 1. 项目概述

“政策智能匹配”是可嵌入城市服务、园区服务、政务门户或企业服务载体的政策服务模块。用户选择个人或企业身份并填写画像后，系统基于结构化规则计算政策匹配度，解释已满足条件与待补条件，并引导用户完成站内模拟申报或前往外部渠道办理。

首版使用通用演示政策库，覆盖人才、就业、创业、惠企、科技创新和补贴等方向，不绑定特定地区，不将演示政策、办理入口或审核结果表述为真实政务信息。

该模块不是独立 App，不使用底部 TabBar。它通过载体入口进入，以一次完整任务为主线，并使用顶部返回、页面内入口和状态卡片组织次级能力。

## 2. 产品目标

1. 让个人和企业通过少量、清晰的分步问题形成可复用画像。
2. 将分散且难理解的政策条件转化为可解释的匹配结果。
3. 明确展示匹配度、已满足条件、待补条件、支持内容和申报期限。
4. 对支持站内办理的政策提供申请、材料、提交和进度记录闭环。
5. 对外部办理政策提供材料清单、办理步骤和外部入口引导，并允许用户记录办理进度。
6. 延续现有 App Portfolio 的模块注册、统一认证、统一 API、Prisma、文件能力和测试约束。

## 3. 产品原则

### 3.1 可解释优先

匹配结论必须能追溯到明确规则。系统不得只给出一个百分比或笼统的 AI 推荐语，而应逐项说明条件判断结果。

### 3.2 任务优先

界面围绕“完善画像—获得匹配—查看政策—准备材料—完成申报”组织，不建设独立应用式导航体系，不把政策目录浏览放在主任务之前。

### 3.3 信息可信

- 所有演示政策均明确标注“演示数据”。
- 外部申报入口为演示占位时必须明确说明，不伪装成真实政府网站。
- 站内申报结果只代表演示流程，不声称已进入真实政务审核。
- 匹配结果是基于用户所填信息的辅助判断，不替代主管部门最终认定。

### 3.4 渐进填写

画像问卷按用户当前任务只收集必要信息。允许暂存、返回修改和复用已有画像，避免每次匹配重复填写。

## 4. 用户与身份

### 4.1 访客

访客可以查看服务介绍、演示政策分类和政策公开详情。开始填写画像、保存匹配结果、收藏或申报时进入现有统一登录流程，登录完成后返回原操作上下文。

### 4.2 个人用户

个人画像包括：

- 基础信息：年龄区间、常住或意向地区、户籍类型。
- 教育与人才：最高学历、专业方向、毕业时间、人才资质、职业资格。
- 就业情况：就业状态、所属行业、工作年限、当前单位类型。
- 创业情况：是否创业、创业阶段、企业成立时间、带动就业情况。
- 其他条件：社保缴纳、困难或特殊群体身份等与演示政策相关的必要信息。

个人用户可以执行匹配、查看解释、收藏政策、维护画像、发起申报并查看记录。

### 4.3 企业用户

企业画像包括：

- 基础信息：企业名称、行业、企业规模、成立时间、登记地区。
- 经营情况：营收区间、纳税情况、经营状态、发展阶段。
- 创新能力：研发投入、研发人员、高新技术或专精特新等资质。
- 用工情况：员工规模、新增就业、重点人群吸纳情况。
- 项目情况：当前项目阶段、投资区间、知识产权和成果转化情况。

企业用户可以执行匹配、查看解释、收藏政策、维护企业画像、发起申报并查看记录。

### 4.4 身份切换

- 首次进入必须先选择“个人匹配”或“企业匹配”。
- 两类画像、匹配记录和申请单相互独立。
- 用户可从服务入口页或轻量个人中心切换身份。
- 切换身份前保存当前草稿，不清空另一身份下的历史数据。

## 5. 信息架构与核心流程

应用地址为 `/policy-match`，不设置底部导航。

核心流转为：

`载体入口 → 身份选择 → 画像填写 → 智能分析 → 匹配结果 → 政策详情 → 站内申报或外部引导 → 进度记录`

所有次级页面使用顶部返回导航。收藏、历史匹配、画像维护和申报记录从服务入口页的状态区或页面右上角入口进入，不形成独立 TabBar。

## 6. 页面需求与内容结构

### 6.1 服务入口页

页面目标是帮助用户快速开始或继续一项政策任务。

内容顺序：

1. 载体上下文中的简洁页头、服务名称和必要的关闭或返回入口。
2. 核心价值说明：填写情况，发现可能申报的政策。
3. “个人匹配 / 企业匹配”双入口，并解释两者分别需要准备的信息。
4. 已登录用户的画像完成度和“继续完善 / 重新匹配”操作。
5. 最近一次匹配摘要：匹配时间、身份、可申报数量和最高匹配度。
6. 进行中的申报：政策名称、当前状态、下一步动作和更新时间。
7. 热门演示政策，以少量列表提供辅助浏览，不抢占匹配入口的优先级。
8. 历史匹配、收藏和全部申报记录入口。

未登录或没有历史数据时，不显示空白管理区，改为说明完成匹配后可获得的结果。

### 6.2 画像问卷页

页面使用线性分步流程，不在一个长表单中一次展示全部字段。

通用结构：

1. 顶部返回、当前身份和保存退出。
2. 步骤名称、进度和“为什么需要这些信息”的简短说明。
3. 当前步骤表单，优先使用单选、多选、分段选择和区间选择。
4. 对匹配有决定性影响的字段提供解释，不使用模糊术语。
5. 底部固定“上一步 / 下一步”，最后一步为“开始智能匹配”。
6. 自动保存已完成步骤，并显示最近保存状态。

个人流程建议拆为：基础情况、教育与人才、就业与社保、创业情况、确认信息。

企业流程建议拆为：企业基础、经营情况、创新资质、用工与项目、确认信息。

用户可以选择“不确定”。系统应将其标记为待补信息，并在结果中说明该字段可能影响匹配准确性。

### 6.3 匹配分析页

分析过程展示三个阶段：读取画像、核对政策条件、生成匹配解释。每个阶段完成后提供简短反馈，避免只显示无意义的旋转加载。

规则计算完成后自动进入结果页。失败时保留画像并提供重试，不要求用户重新填写。

### 6.4 匹配结果页

页面内容：

1. 本次匹配摘要：身份、画像完整度、分析政策数量和结果更新时间。
2. 结果总览：可申报、可能符合、暂不符合的数量。
3. 分类筛选：人才、就业、创业、惠企、科技创新和补贴。
4. 排序：综合匹配度、截止时间、支持力度。
5. 政策结果卡：名称、类别、匹配度、结论、支持摘要、截止时间、已满足与待补条件数量。
6. 每张卡片提供“查看详情”，符合收藏条件时可收藏。
7. 支持选择两项政策进行条件对比；移动端使用纵向分组对比，不使用横向超宽表格。

结果分级：

- `可申报`：全部硬性条件满足，且必要画像字段完整。
- `可能符合`：硬性条件未被明确否定，但存在未知字段或可补充条件。
- `暂不符合`：至少一项硬性条件明确不满足。

“暂不符合”政策默认折叠在次级区域，但用户仍可查看具体原因。

### 6.5 政策详情页

内容顺序：

1. 政策名称、演示标识、类别、申报状态和截止时间。
2. 支持方式、额度或权益范围、适用对象和办理渠道。
3. 本次匹配结论与匹配度。
4. 已满足条件、待补条件和不满足条件，逐项展示对应画像依据。
5. “补充信息后重新判断”入口，返回画像的相关步骤。
6. 申报材料清单，区分必需、按情况提供和已准备。
7. 办理流程、预计步骤和注意事项。
8. 政策说明、演示来源和咨询说明。
9. 固定主操作：站内申报政策显示“开始申报”；外部办理政策显示“查看办理指南”。

匹配度不得替代结论。存在硬性条件不满足时，即使评分条件较高，也不能显示为“可申报”。

### 6.6 站内申报页

站内申报按以下步骤组织：

1. 确认申请主体与政策。
2. 填写政策要求的补充申请信息。
3. 上传或关联材料，并查看格式、大小和有效期要求。
4. 预览全部申请内容和承诺说明。
5. 提交申请并展示演示受理编号。

申请支持自动保存草稿。提交前服务端重新验证政策状态、身份、硬性条件和必需材料。提交后进入只读状态，需补充材料时由独立补充流程处理，不直接修改已提交版本。

### 6.7 外部办理指南页

页面内容：

1. 办理渠道说明和演示入口提示。
2. 分步骤办理说明。
3. 可勾选的材料准备清单。
4. 容易遗漏的条件与注意事项。
5. 外部办理按钮；演示环境不得跳转到虚构的真实政府域名。
6. “标记为已前往办理”操作，用于在申报记录中保留用户进度。

外部办理状态由用户主动记录，不生成“审核通过”等无法验证的状态。

### 6.8 申报记录页与详情

列表按进行中、已提交、需补充、已完成和已终止分组，展示政策名称、申请主体、办理方式、状态、更新时间和下一步动作。

详情页展示：

- 申请摘要和演示受理编号。
- 材料完成情况。
- 状态时间线。
- 当前待办与截止时间。
- 可执行的补材料、撤回草稿或继续外部办理操作。

### 6.9 个人中心轻页面

该页面只承载辅助管理，不作为独立导航中心。内容包括身份切换、个人与企业画像维护、收藏政策、历史匹配和数据说明。

### 6.10 通用状态

必须覆盖：

- 未选择身份。
- 画像为空或不完整。
- 无匹配结果。
- 匹配计算失败。
- 政策已截止或已下架。
- 材料缺失、格式错误或上传失败。
- 重复提交。
- 申请状态已被其他操作更新。
- 网络异常和服务暂不可用。

所有失败状态优先保留用户已填写内容，并给出明确的恢复动作。

## 7. 匹配规则

### 7.1 规则类型

每条政策由以下规则组成：

- 硬性条件：不满足时结论为暂不符合。
- 评分条件：满足后增加匹配分，用于同类政策排序。
- 信息条件：缺失时不直接判定不符合，但降低结果置信度并提示补充。
- 材料条件：不参与主体资格判定，用于申报准备度计算。

### 7.2 匹配度

- 匹配度采用 0–100 的整数分值。
- 硬性条件先于评分计算。
- 评分条件按政策配置权重归一化计算。
- 未知字段不视为满足，也不等同于明确不满足。
- 结果同时保存规则版本、政策版本和画像快照。

### 7.3 解释结果

每个条件返回：规则名称、判断状态、用户画像依据、政策要求和建议动作。状态包括 `matched`、`missing`、`unmatched` 和 `not_applicable`。

### 7.4 重新匹配

用户修改画像后可重新执行匹配。新的结果生成独立快照，历史匹配不被覆盖。

## 8. 申报与状态规则

### 8.1 办理方式

- `internal`：站内完整模拟申报。
- `external`：展示外部办理指南并记录用户进度。

每条政策仅配置一种首要办理方式，避免同一政策出现两个含义不清的主操作。

### 8.2 站内申请状态

状态包括：

- `draft`：草稿。
- `submitted`：已提交。
- `supplement_required`：需补充材料。
- `under_review`：演示审核中。
- `approved`：演示审核通过。
- `rejected`：演示审核未通过。
- `withdrawn`：已撤回。

状态变化必须写入时间线。演示审核状态由种子数据或明确的演示流程驱动，并持续标注为演示结果。

### 8.3 外部办理记录状态

状态包括 `preparing`、`visited_external` 和 `stopped`，不包含无法由本系统验证的审核结论。

### 8.4 重复与并发

- 同一用户、同一申请主体和同一政策只能有一个活动中的站内申请。
- 提交接口必须幂等，防止重复点击产生多份申请。
- 更新草稿和补充材料时校验版本，发现并发更新则提示刷新后继续。

## 9. 数据与媒体要求

- PostgreSQL 是业务数据的唯一事实来源。
- Prisma migration 管理数据结构变更，Prisma seed 提供可体验的政策、画像和申请状态数据。
- 文件通过统一文件能力保存，数据库只记录文件标识、名称、类型、大小和业务关系。
- 政策必须包含版本、有效期、状态、办理方式、演示来源和规则配置。
- 匹配快照必须保留当次画像、政策版本、规则版本、得分和逐项解释。
- 种子数据至少覆盖高匹配、信息缺失、硬性条件不符、即将截止、已截止、站内申报、外部办理、草稿、需补材料和已完成状态。

## 10. 后端模块与接口边界

后端模块位于 `apps/api/src/modules/policy-match`，按项目约束拆分路由、校验、控制器、服务、领域规则和数据库访问。

业务边界建议包括：

- 画像：读取、创建、更新个人或企业画像。
- 政策：政策列表、筛选、详情和收藏。
- 匹配：执行匹配、读取快照和政策对比。
- 申请：创建草稿、更新信息、提交、补材料和查询状态。
- 外部办理：保存材料准备进度和外部办理标记。

所有身份和数据归属由统一认证信息确定，不相信前端传入的用户 ID。外部输入统一在 Validation 层校验，业务状态和匹配规则在 Service 或 Domain 层处理。

## 11. 前端模块边界

前端模块位于 `apps/web/src/modules/policy-match`。

- 页面负责路由参数、页面状态和业务组件编排。
- 问卷步骤、匹配摘要、政策卡、条件解释、材料清单、申报时间线等复杂区块拆为业务组件。
- 数据请求通过按实体或能力拆分的 Service 调用，不在页面或组件中直接访问 Axios。
- 跨页面画像草稿和申请草稿可以使用模块内 Store 或 Hook 管理，并以服务端数据为准。
- 模块不深层引用其他业务模块，只使用 `shared` 中的统一 API、身份和文件能力。

## 12. 错误处理与安全

- 画像字段按身份和步骤校验，服务端拒绝不属于当前身份的字段组合。
- 匹配接口限制执行频率，防止无意义重复计算。
- 上传材料校验文件类型、大小和归属，下载使用统一文件权限。
- 申请详情、材料和匹配快照只能由所属用户访问。
- 政策失效、规则更新或申请状态变化时返回明确业务错误，不以通用 500 替代。
- 日志不记录证件号码、联系方式、材料内容等敏感信息。
- 前端不在本地持久化完整敏感画像或材料地址。

## 13. 测试与验收

### 13.1 后端测试

- 个人与企业画像字段校验及数据隔离。
- 硬性条件、评分条件、未知字段和权重归一化。
- 匹配结论与匹配度不冲突。
- 匹配快照在画像或政策更新后仍可还原。
- 站内申请草稿、提交、补充材料和状态流转。
- 重复提交、政策截止、材料缺失和并发更新。
- 未授权用户不能读取他人的画像、快照、申请或材料。

### 13.2 前端测试

- 无 TabBar，且核心流程的返回关系正确。
- 个人与企业问卷展示各自字段并可暂存恢复。
- 分析、成功、空、失败和重试状态完整。
- 匹配卡、筛选、排序、详情解释和对比可用。
- 站内申报与外部办理显示不同主操作和状态。
- 320px 起无横向滚动，固定操作区不遮挡内容与系统安全区。

### 13.3 完成标准

1. 用户能完成个人或企业画像并获得规则可解释的匹配结果。
2. 结果明确区分可申报、可能符合和暂不符合。
3. 用户能从政策详情完成一条站内模拟申报闭环。
4. 用户能按指南准备一条外部办理政策并记录进度。
5. 重新进入服务时可继续画像、匹配或申请任务。
6. 演示数据、外部入口和审核结果均无真实政务误导。
7. 前后端遵守各自 `AGENTS.md`，必要测试、lint 和 build 通过。

## 14. 首版不包含

- 真实政府政策库抓取、OCR 入库或自动更新。
- 大模型判断、对话式政策顾问或生成式申报材料。
- 真实统一申报平台对接、电子签章、支付或短信服务。
- 管理后台、政策编辑器和可视化规则编排器。
- 跨地区真实政策口径比较。
- 自动认定用户资格或替代主管部门审核。
